1. Overview

RESQ is an emergency-dispatch platform with a Next.js web admin dashboard and an Expo/React Native mobile app, backed by Supabase (Postgres, Auth, Realtime, Storage) and deployed on Vercel. It routes an emergency report — triggered from the app, SMS, USSD, or a phone call — to the responder(s) best placed to handle it, based on the reporting person's institution (or, for the general public, the nearest institution that opted in), the emergency type, and location.

RESQ is a routing and coordination tool. It is not a replacement for national emergency services where those are directly reachable and appropriate.

4. Institution Types

TypeSet byBehaviour
PrivateDefault (super admin can flip visibility) Reachable only by users who enter its institution code. Not location-matched.
Public — single serviceInstitution admin, with only internal responders (no partner units) Serves the general public directly. Its own coordinates + enabled types decide who gets routed to it.
Public — companyInstitution admin, with one or more partner units (each with their own unit admin) Same structure as above, plus its own partner units (hospitals, police posts, etc.), each independently routable by their own coordinates and type once a public emergency lands on the parent institution.

There is no separate database flag for "single service" vs "company" — it's simply whether the institution has registered any partner units. Both are still governed by the same visibility = 'public' flag and enabled_emergency_types the institution admin chose.

5. Emergency Response Flow Diagram

From the moment a user triggers an SOS to resolution, every branch.

Responder-availability gate hardened: before any emergency record is created — from the app, SMS, or USSD — RESQ checks whether an active, full-permission responder actually exists for that specific emergency type (an institution-wide responder whose responder_emergency_types covers it, or a partner unit matching by type + distance with at least one non-view-only responder). If nobody qualifies, the report is rejected before it's ever written to the database — a public user is told no public responder is currently available for that type; a private user is told their institution has no one available and to contact them directly or call local emergency services. This is type-specific: an institution with only a medical responder can no longer silently swallow a GBV or fire report. Every rejection is logged as trigger_blocked_no_responder, visible live in the Super Admin Terminal.

7. Permission Model

Enforced at two independent layers, so a bypassed UI can never grant more access than intended:

  1. Row-Level Security (Postgres/Supabase) — every table's policies check the caller's role and institution/unit via auth_role() / auth_institution_id() / auth_service_id().
  2. API routes (service-role, server-side) — re-check role, institution, and (for claim/resolve) responder_permission before writing, independent of RLS.

Notable protections added during hardening:

  • A secondary (view_only) responder is blocked from claiming both in the claim API route and again at the RLS/trigger level — a bypassed UI still can't claim.
  • Column-level protection on profiles and institutions (via triggers/grants) stops a logged-in user from writing security-sensitive columns (role, institution, subscription tier, status, etc.) even on a row they otherwise have UPDATE access to.
  • new Institution join codes and institution-admin verification codes are now throttled at the database layer (8 failed guesses per rolling 5-minute window, per account) — this holds no matter which client calls the RPC (web, mobile, or a raw REST request), since it's enforced inside the Postgres function itself, not just in application code.
  • new Cron endpoints (/api/cron/escalate, /api/cron/weekly-report) compare their shared secret using a constant-time comparison, closing a timing side-channel that a plain string comparison leaves open.

8. Key Features

  • AI-generated immediate safety guidance per emergency type (Groq).
  • SMS / USSD / voice-call triggering for users without the app (Africa's Talking) — now gated by the same responder-availability check as the app.
  • Live chat (text, photo, voice note) between the reporting user and the responder, and a separate institution- wide team chat, with in-chat abuse reporting.
  • Live location updates (~15s) while an emergency is active, shown on an in-app tracking map (Leaflet on web, react-native-maps on mobile) rather than only a link to an external maps app.
  • Case rating after resolution.
  • Weekly case-summary emails to institution admins, plus on-demand case/report downloads.
  • Push notifications, offline SMS fallback for responders.
  • Distance + type based dispatch (pickMatchingServices) for every partner unit, always applied regardless of how many units an institution has — and, as of this update, applied consistently to whether an emergency can be created at all, not only to who gets notified afterward.
  • Self-service account deletion and in-app content reporting (Google Play pre-approval requirements).
  • Glassmorphic, spring-physics animated UI across the login page and both admin dashboards (Tailwind CSS + Framer Motion on web, Moti + react-native-reanimated on mobile).

10. Security & Data

  • Chat text for a resolved case is deleted once its weekly report has been emailed (the report becomes the institution's copy).
  • Core emergency records (type, who handled it, timestamps, rating) are retained indefinitely as case history.
  • If an institution is deleted, a full export is taken first for RESQ's own records before permanent removal.
  • An emergency can only ever be created for an institution/unit with an active, full-permission responder who actually handles that specific type — enforced identically across the app, SMS, and USSD trigger paths.
  • Institution join codes (~1.29 billion possible combinations, generated with a cryptographically secure RNG) and institution-admin verification codes are throttled at the database layer against repeated guessing.
  • No secret keys are ever exposed to a client bundle — only the public Supabase URL and anon key are shipped to web/mobile clients; every service-role operation runs server-side only.
  • No raw SQL string-building anywhere user input reaches the database — all lookups (institution codes, chat content, etc.) go through parameterized queries or Postgres RPC functions, not string concatenation.
  • Full Terms of Service and Privacy Policy: /terms and /privacy on the web app (the mobile app links to the same two pages, so there is only one copy of each to keep current).

11. Current Status & Known Gaps

  • Email delivery (Supabase Auth confirm/reset emails, weekly reports): the project's Resend account has no verified sending domain, so mail still goes out from the shared onboarding@resend.dev sandbox address — which only delivers to the Resend account owner's own email. Institution admins are very likely not receiving weekly report emails today. The weekly-report sender is now configurable via RESEND_FROM_EMAIL, so once a domain is purchased and verified with Resend, this is a one-line env var fix rather than a code change. Supabase's own auth emails would still need either Gmail SMTP configured in Supabase (quick, free, fixes only those emails) or the same verified domain.
  • Mobile EAS builds: free-tier build quota exhausted, resets ~Oct 2026 unless the Expo plan is upgraded. The in-app tracking map (react-native-maps) and other native modules added recently work fine in Expo Go for development/testing, but shipping them to real users needs a new production build once quota allows.
  • Database migrations: everything through day42 (the join/verification code brute-force guard) is confirmed applied — verified live against the database, not just checked off from the migration files.
  • Hosting: deployed on Vercel's free Hobby tier at a default *.vercel.app URL, with no custom domain. Vercel's Hobby plan terms of service restrict commercial/for-profit use — a Pro plan and a custom domain are worth doing before treating this as an official, public-facing service.
  • No automated test suite or CI pipeline yet. Correctness currently relies on manual testing and production builds compiling cleanly, not on unit/integration/e2e tests.
  • Public pages show a contact email but no formal business/registration details (legal entity name, address) — add once that information is decided; not fabricated here.
  • Privacy policy doesn't yet address use by minors — worth adding explicit language if institutions using RESQ include schools or otherwise serve users under 18.
